# 📤 Upload de arquivos com Spring Framework (back-end)

O projeto parte do código do servidor da **aula04** (Spring Boot 4, Java 25, Spring Security, JWT, MapStruct e autenticação com o Google por meio do ID Token). Nesta aula foi adicionado o **upload de uma imagem** para a entidade `Product`, armazenada de duas formas diferentes:

- **Sistema de arquivos (disco)**: o arquivo é gravado em uma pasta do servidor e o banco de dados armazena apenas o **nome** do arquivo;
- **Banco de dados**: o conteúdo do arquivo (*bytes*) é armazenado em uma coluna do tipo `BLOB` da tabela de produtos.

| | Sistema de arquivos | Banco de dados |
| --- | --- | --- |
| Onde fica o arquivo | Pasta `app.upload.directory` | Coluna `image_file` (BLOB) |
| O que fica no banco | Nome do arquivo (`image_name`) | Conteúdo e nome do arquivo (`image_file`, `image_file_name`) |
| Vantagens | Banco de dados menor; arquivos podem ser servidos por um servidor web ou CDN | *Backup* e transação únicos; não depende do disco do servidor |
| Desvantagens | É necessário fazer *backup* da pasta; não funciona com várias instâncias da API sem um disco compartilhado | Banco de dados cresce rapidamente; consultas que retornam a imagem ficam mais pesadas |

## 📋 Resumo das alterações

- **`model/Product.java`** e **`dto/ProductDTO.java`**: novos atributos `imageName`, `imageFile` e `imageFileName`.
- **`db/*/V1.0__Init.sql`**: novas colunas na tabela `tb_product`.
- **`application.yml`**: pasta de *upload* (`app.upload.directory`) e tamanho máximo dos arquivos.
- **`service/IProductService.java`** e **`service/impl/ProductServiceImpl.java`**: métodos para salvar a imagem no disco ou no banco de dados e para ler a imagem do disco em Base64.
- **`controller/ProductController.java`**: *endpoints* `POST /products/upload-fs` e `POST /products/upload-db`.
- **`error/ExceptionHandlerAdvice.java`**: tratamento da `IllegalArgumentException` (imagem inválida) com HTTP 400.
- **`.gitignore`**: a pasta `uploads/` não é versionada.

## 1. 🧱 Entidade, DTO e banco de dados

Na classe **Product** foram adicionados os atributos que armazenam os dados da imagem:

```java
@Column(name = "image_name")
private String imageName; // Upload no Sistema de Arquivos (disco)

@Lob
@Column(name = "image_file")
private byte[] imageFile; // Upload no Banco de dados

@Column(name = "image_file_name")
private String imageFileName; // Upload no Banco de dados
```

A anotação **`@Lob`** (*Large Object*) indica que o atributo armazena um conteúdo grande, mapeado para uma coluna do tipo `BLOB` (*Binary Large Object*) no banco de dados.

Os mesmos atributos foram adicionados ao **ProductDTO**. O **ProductMapper** (MapStruct) converte os novos atributos automaticamente, pois eles possuem o mesmo nome na entidade e no DTO. Ao serializar o DTO em JSON, o Jackson converte o `byte[] imageFile` em uma *string* **Base64**, que o front-end utiliza diretamente em uma imagem (`<img src="data:image;base64,...">`).

```java
private String imageName; // Upload no Sistema de Arquivos (disco)

private byte[] imageFile; // Upload no Banco de dados (enviado no JSON em Base64)

private String imageFileName; // Upload no Banco de dados
```

Como o banco de dados é versionado com o **Flyway**, as colunas foram adicionadas na tabela `tb_product` dos *scripts* `V1.0__Init.sql`:

```sql
create table tb_product (
                         id bigint generated by default as identity,
                         description varchar(1024) not null,
                         name varchar(100) not null,
                         price double not null,
                         category_id bigint,
                         image_name varchar(255),
                         image_file_name varchar(255),
                         image_file blob,
                         primary key (id)
);
```

> No PostgreSQL o tipo equivalente ao `blob` é o `bytea`.

## 2. ⚙️ Configuração

No **`application.yml`** foram adicionadas a pasta em que os arquivos são gravados e o tamanho máximo dos arquivos enviados (o padrão do Spring Boot é 1MB):

```yaml
spring:
  # Tamanho máximo dos arquivos enviados no upload (o padrão do Spring Boot é 1MB)
  servlet:
    multipart:
      max-file-size: 5MB
      max-request-size: 5MB

app:
  upload:
    # Pasta em que as imagens enviadas no upload para o sistema de arquivos são armazenadas.
    # Caminho relativo à pasta em que a aplicação é executada (ou absoluto, ex.: /uploads)
    directory: ${UPLOAD_DIRECTORY:uploads}
```

Por padrão os arquivos são gravados em `server/uploads/images-product`. A pasta pode ser alterada com a variável de ambiente `UPLOAD_DIRECTORY`. A pasta `uploads/` foi adicionada ao **`.gitignore`**, pois os arquivos enviados pelos usuários não devem ser versionados.

## 3. 🗂️ Service: salvando a imagem

Na interface **IProductService** foram adicionados os métodos:

```java
public interface IProductService extends ICrudService<Product, Long> {

    void saveImageFileToDisk(MultipartFile file, Product product);

    void saveImageFileToDatabase(MultipartFile file, Product product);

    String getProductImageFileFromDisk(Long id);
}
```

O arquivo enviado é recebido como um **`MultipartFile`**, que disponibiliza o nome original do arquivo (`getOriginalFilename()`), o tipo do conteúdo (`getContentType()`) e os *bytes* do arquivo (`getBytes()`).

### 3.1 Validando o arquivo

Antes de salvar, a imagem é validada. O nome do arquivo é informado pelo cliente e **não é confiável**: somente a extensão é aproveitada, e apenas se estiver na lista de extensões permitidas. O arquivo é sempre gravado com o nome `<id do produto>.<extensão>` (ex.: `1.png`):

```java
// Extensões de imagem aceitas no upload
private static final Set<String> ALLOWED_EXTENSIONS = Set.of(".jpg", ".jpeg", ".png", ".gif", ".webp");

private String getImageExtension(MultipartFile file) {
    if (file == null || file.isEmpty()) {
        throw new IllegalArgumentException("Nenhuma imagem foi enviada.");
    }
    String contentType = file.getContentType();
    if (contentType == null || !contentType.startsWith("image/")) {
        throw new IllegalArgumentException("O arquivo enviado não é uma imagem.");
    }
    String originalFilename = file.getOriginalFilename();
    int dot = originalFilename == null ? -1 : originalFilename.lastIndexOf('.');
    String extension = dot < 0 ? "" : originalFilename.substring(dot).toLowerCase(Locale.ROOT);
    if (!ALLOWED_EXTENSIONS.contains(extension)) {
        throw new IllegalArgumentException("Extensão de imagem não permitida. Utilize: " + ALLOWED_EXTENSIONS);
    }
    return extension;
}
```

> ⚠️ **Por que validar a extensão?** Se a extensão fosse simplesmente copiada do nome enviado, um nome como `imagem.png/../../arquivo` resultaria na "extensão" `.png/../../arquivo`, e o arquivo seria gravado **fora** da pasta de *upload* (ataque conhecido como *path traversal*). Além disso, um nome sem `.` causaria uma exceção. A validação do `contentType` sozinha não é suficiente, pois ele também é informado pelo cliente.

A `IllegalArgumentException` é tratada no **ExceptionHandlerAdvice**, retornando **HTTP 400** com a mensagem do erro:

```java
// Erros de validação lançados pelos services, ex.: arquivo de imagem inválido no upload
@ExceptionHandler({IllegalArgumentException.class})
@ResponseStatus(HttpStatus.BAD_REQUEST)
public ApiError handlerValidationException(IllegalArgumentException exception,
                                           HttpServletRequest request) {
    return new ApiError(HttpStatus.BAD_REQUEST.value(), exception.getMessage(),
            request.getServletPath(), null);
}
```

### 3.2 Salvando no sistema de arquivos

A pasta é lida da propriedade `app.upload.directory` no construtor da classe **ProductServiceImpl**:

```java
private final ProductRepository productRepository;
// Pasta em que as imagens são armazenadas no sistema de arquivos (propriedade app.upload.directory)
private final Path imagesDirectory;

public ProductServiceImpl(ProductRepository productRepository,
                          @Value("${app.upload.directory}") String uploadDirectory) {
    this.productRepository = productRepository;
    this.imagesDirectory = Path.of(uploadDirectory, "images-product").toAbsolutePath().normalize();
}
```

O método `saveImageFileToDisk` valida a imagem, salva o produto (para gerar o `id`, utilizado no nome do arquivo), grava o arquivo com a API `java.nio.file.Files` e atualiza o atributo `imageName`:

```java
@Override
@Transactional
public void saveImageFileToDisk(MultipartFile file, Product product) {
    String extension = getImageExtension(file);
    productRepository.save(product); // gera o id do produto, utilizado no nome do arquivo
    String fileName = product.getId() + extension;
    try {
        Files.createDirectories(imagesDirectory);
        Files.write(imagesDirectory.resolve(fileName), file.getBytes());

        product.setImageName(fileName);
        productRepository.save(product);
    } catch (IOException e) {
        log.error("Error in saveImageFileToDisk() - {}", e.getMessage());
        throw new UncheckedIOException(e);
    }
}
```

Como o método é **`@Transactional`**, o produto e a imagem são salvos na mesma transação: se a imagem for inválida ou ocorrer um erro ao gravar o arquivo, o produto também não é salvo.

### 3.3 Salvando no banco de dados

O método `saveImageFileToDatabase` armazena os *bytes* do arquivo no atributo `imageFile`, que é persistido na coluna `BLOB`:

```java
@Override
@Transactional
public void saveImageFileToDatabase(MultipartFile file, Product product) {
    String extension = getImageExtension(file);
    productRepository.save(product); // gera o id do produto, utilizado no nome do arquivo
    try {
        product.setImageFileName(product.getId() + extension);
        product.setImageFile(file.getBytes());
        productRepository.save(product);
    } catch (IOException e) {
        log.error("Error in saveImageFileToDatabase() - {}", e.getMessage());
        throw new UncheckedIOException(e);
    }
}
```

### 3.4 Lendo a imagem do disco em Base64

Para enviar ao front-end uma imagem armazenada em disco no mesmo formato da imagem armazenada no banco de dados, o método `getProductImageFileFromDisk` lê o arquivo e o converte para Base64 com a classe `java.util.Base64`:

```java
@Override
public String getProductImageFileFromDisk(Long id) {
    Product product = productRepository.findById(id).orElse(null);
    if (product == null || product.getImageName() == null) {
        return null;
    }
    try {
        byte[] image = Files.readAllBytes(imagesDirectory.resolve(product.getImageName()));
        return Base64.getEncoder().encodeToString(image);
    } catch (IOException e) {
        log.error("Error in getProductImageFileFromDisk() - {}", e.getMessage());
        throw new UncheckedIOException(e);
    }
}
```

> Nas versões anteriores eram utilizadas as bibliotecas `commons-io` e `commons-codec` para ler o arquivo e gerar o Base64. As classes `java.nio.file.Files` e `java.util.Base64` do próprio Java fazem o mesmo, sem dependências adicionais.

## 4. 🚪 Controller: recebendo o arquivo

Para enviar um arquivo junto com os dados do produto, a requisição utiliza o formato **`multipart/form-data`**, composto por "partes": a parte `product` contém o JSON do produto e a parte `image` contém o arquivo. No **ProductController** cada parte é recebida com a anotação **`@RequestPart`**:

```java
/* Upload de arquivo salvo no sistema de arquivos
   multipart/form-data = { product: {JSON do produto}, image: arquivo }
*/
@PostMapping(value = "upload-fs", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public ResponseEntity<ProductDTO> saveImageFileToDisk(@RequestPart("product") @Valid ProductDTO productDTO,
                                                      @RequestPart("image") MultipartFile file) {
    Product product = toEntity(productDTO);
    productService.saveImageFileToDisk(file, product);
    return ResponseEntity.status(HttpStatus.CREATED).body(toDto(product));
}

/* Upload de arquivo salvo no Banco de dados
   multipart/form-data = { product: {JSON do produto}, image: arquivo }
*/
@PostMapping(value = "upload-db", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public ResponseEntity<ProductDTO> saveImageFileToDatabase(@RequestPart("product") @Valid ProductDTO productDTO,
                                                          @RequestPart("image") MultipartFile file) {
    Product product = toEntity(productDTO);
    productService.saveImageFileToDatabase(file, product);
    return ResponseEntity.status(HttpStatus.CREATED).body(toDto(product));
}
```

- Assim como nos demais *endpoints*, o *controller* recebe e retorna o **ProductDTO**, convertido com os métodos `toEntity` e `toDto` (MapStruct). A anotação `@Valid` valida os dados do produto.
- Para que o Spring converta a parte `product` em um objeto, ela deve ser enviada com o tipo `application/json`. No front-end isso é feito com um `Blob`:
  ```ts
  const formData = new FormData();
  formData.append("image", image);
  formData.append("product", new Blob([JSON.stringify(data)], { type: "application/json" }));
  ```
- Os *endpoints* estão em `/products/**`, portanto exigem um usuário com a permissão `ROLE_ADMIN` (regras do **WebSecurity**).

## 5. 🧪 Testando

Com a API em execução, obtenha o *token* do usuário `admin` (senha `123`) e envie um produto com imagem:

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/login -H "Content-Type: application/json" \
        -d '{"username":"admin","password":"123"}' | sed -E 's/.*"token":"([^"]*)".*/\1/')

echo '{"name":"Produto Teste","description":"Produto com imagem","price":10.5,"category":{"id":1}}' > product.json

# Upload salvo no banco de dados
curl -H "Authorization: Bearer $TOKEN" \
     -F "product=@product.json;type=application/json" \
     -F "image=@imagem.png;type=image/png" \
     http://localhost:8080/products/upload-db

# Upload salvo no sistema de arquivos
curl -H "Authorization: Bearer $TOKEN" \
     -F "product=@product.json;type=application/json" \
     -F "image=@imagem.png;type=image/png" \
     http://localhost:8080/products/upload-fs
```

Resposta (HTTP 201) do *upload* no banco de dados, com a imagem em Base64:

```json
{ "id": 9, "name": "Produto Teste", ..., "imageName": null, "imageFile": "iVBORw0KGgoAAAANSUhEUg...", "imageFileName": "9.png" }
```

No *upload* para o sistema de arquivos, a resposta contém `"imageName": "10.png"` e o arquivo é gravado em `server/uploads/images-product/10.png`. Um arquivo com extensão não permitida retorna **HTTP 400**:

```json
{ "status": 400, "message": "Extensão de imagem não permitida. Utilize: [.gif, .jpg, .jpeg, .webp, .png]", "url": "/products/upload-fs" }
```
