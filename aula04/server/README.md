# 🔐 Autenticação com redes sociais em uma aplicação com Spring Framework (back-end)

Na aplicação desenvolvida até a **aula03** (Spring Boot 4, Spring Security, JWT e MapStruct), o usuário se autenticava enviando `username` e `password` para a URL `/login`, onde o filtro **JWTAuthenticationFilter** validava as credenciais e devolvia um *token* JWT. Nesta aula a API passa a aceitar também a autenticação com uma **conta Google**.

O Google é responsável por autenticar o usuário e entregar ao front-end um **ID Token** (um JWT assinado pelo Google contendo e-mail, nome, foto, etc.). O papel da API é:

1. Receber esse ID Token do cliente;
2. Validar se ele é autêntico (assinatura), se foi emitido pelo Google (*issuer*) e se foi emitido para a nossa aplicação (*audience* = Client ID);
3. Buscar o usuário pelo e-mail e, caso ainda não exista, cadastrá-lo com a permissão `ROLE_USER`;
4. Gerar e devolver o **JWT da própria API**, no mesmo formato já retornado pelo *login* tradicional.

A partir daí, todas as requisições seguem exatamente o mesmo caminho de antes: o **JWTAuthorizationFilter** valida o JWT enviado no *header* `Authorization` e carrega as *authorities* do usuário.

> A configuração das credenciais no Google Cloud Console está descrita no [README.md](../README.md) da pasta **aula04**.

## 📋 Resumo das alterações

O projeto parte exatamente do código do servidor da **aula03**. As alterações realizadas foram:

- **`pom.xml`**: adicionada a dependência `google-api-client`.
- **`application.yml`**: nova propriedade `google.client-id`.
- **`model/AuthProvider.java`**: novo *enum* que identifica a origem do cadastro do usuário (`local`, `google`, ...).
- **`model/User.java`**: novo atributo `provider`.
- **`db/dev/V1.0__Init.sql` e `V1.1__Data.sql`**: nova coluna `provider` na tabela `tb_user`, e usuários iniciais cadastrados como `local`.
- **`service/UserService.java`**: usuários cadastrados pelo formulário recebem o `provider` `local`.
- **`mapper/UserMapper.java`**: o atributo `provider` é ignorado na conversão do `UserDTO` para `User`.
- **`security/JWTAuthenticationFilter.java`**: bloqueio do *login* com senha para usuários cadastrados via rede social.
- **`security/social/GoogleTokenVerifier.java`**: nova classe responsável por validar o ID Token do Google.
- **`security/social/SocialAuthController.java`**: novo *endpoint* `POST /auth-social`.
- **`security/WebSecurity.java`**: liberação do *endpoint* `/auth-social/**` e regras de autorização por *role*.

## 1. 📦 Dependência e configuração

Para validar o ID Token utilizaremos a biblioteca oficial do Google, que já trata o download (e *cache*) das chaves públicas do Google, a verificação da assinatura e das datas de expiração. No arquivo **`pom.xml`**:

```xml
<!-- Autenticação com o Google - validação do ID Token -->
<dependency>
    <groupId>com.google.api-client</groupId>
    <artifactId>google-api-client</artifactId>
    <version>2.6.0</version>
</dependency>
```

O **Client ID** criado no Google Cloud Console é configurado no **`application.yml`**, e não fixo no código Java. A sintaxe `${GOOGLE_CLIENT_ID:valor}` permite sobrescrever o valor por uma variável de ambiente, útil para utilizar credenciais diferentes em cada ambiente (desenvolvimento, produção):

```yaml
# Client ID OAuth 2.0 criado no Google Cloud Console (deve ser o mesmo configurado no front-end)
google:
  client-id: ${GOOGLE_CLIENT_ID:<SEU_CLIENT_ID>.apps.googleusercontent.com}
```

## 2. 🧑 Identificando a origem do usuário

Como agora um usuário pode ser cadastrado de duas formas (formulário de cadastro ou primeiro acesso via Google), é necessário armazenar a **origem** do cadastro. Para isso foi criado o *enum* **AuthProvider**, em **`model/AuthProvider.java`**. Já foram previstos outros provedores para que a aplicação possa ser estendida futuramente (Facebook, GitHub):

```java
package br.edu.utfpr.pb.pw45s.server.model;

public enum AuthProvider {
    local,
    facebook,
    google,
    github
}
```

E na classe **User** foi adicionado o atributo `provider`, persistido como texto (`EnumType.STRING`):

```java
// Origem do cadastro do usuário: local (formulário) ou rede social (google, ...)
@Enumerated(EnumType.STRING)
@Column(length = 20)
private AuthProvider provider;
```

### 2.1 Ajustando os scripts do banco de dados

Como o projeto utiliza o **Flyway** para versionar o banco de dados, a nova coluna foi adicionada no *script* de criação das tabelas, em **`db/dev/V1.0__Init.sql`** (os *scripts* de `db/prod` e `db/test` já possuíam a coluna):

```sql
create table tb_user (
                         id bigint generated by default as identity,
                         display_name varchar(255),
                         password varchar(255),
                         username varchar(255),
                         provider varchar(20), -- adicionado
                         primary key (id)
);
```

E os usuários cadastrados inicialmente, em **`db/dev/V1.1__Data.sql`** (e `import.sql`), passam a informar o provedor `local`:

```sql
INSERT INTO tb_user(provider, display_name, username, password) VALUES ('local', 'Administrador', 'admin','$2a$10$.PVIfB07x.SfMYTcToxL0.yxcLWU0GbS2NUO1W1QAvqMm/TsFhVem');
INSERT INTO tb_user(provider, display_name, username, password) VALUES ('local', 'Teste', 'teste','$2a$10$.PVIfB07x.SfMYTcToxL0.yxcLWU0GbS2NUO1W1QAvqMm/TsFhVem');
```

> 💡 Em um banco de dados que já está em produção, o correto seria **não alterar** um *script* já executado, e sim criar uma nova migração (por exemplo `V1.2__Add_Provider.sql`) com `alter table tb_user add column provider varchar(20);`. Como aqui o banco é recriado a cada execução (H2 em memória), o *script* original foi alterado.

### 2.2 Definindo o provider no cadastro tradicional

O cadastro pelo formulário (`POST /users`) recebe um **UserDTO**, que não possui o atributo `provider` (o cliente não deve escolher a origem do cadastro). Por isso, no **UserMapper** o atributo é explicitamente ignorado na conversão, evitando o aviso de *unmapped target property* do MapStruct:

```java
@Mapping(target = "id", ignore = true)
@Mapping(target = "provider", ignore = true)          // definido no UserService
@Mapping(target = "userAuthorities", ignore = true)   // definido no UserService
User toEntity(UserDTO dto);
```

E o **UserService** define o `provider` como `local` quando ele não foi informado. O mesmo método `save` é utilizado para cadastrar os usuários vindos do Google, que já chegam com o `provider` preenchido. Em ambos os casos o usuário recebe a permissão `ROLE_USER`:

```java
public void save(User user) {
    user.setPassword( passwordEncoder.encode(user.getPassword()) );

    // Usuários cadastrados pelo formulário (POST /users) não informam o provider
    if (user.getProvider() == null) {
        user.setProvider(AuthProvider.local);
    }

    Set<Authority> authorities = new HashSet<>();
    authorities.add(authorityRepository.findByAuthority("ROLE_USER"));
    user.setUserAuthorities(authorities);

    this.userRepository.save(user);
}
```

## 3. ✅ Validando o ID Token do Google

A classe **GoogleTokenVerifier**, criada em **`security/social/GoogleTokenVerifier.java`**, utiliza o `GoogleIdTokenVerifier` da biblioteca do Google para validar o *token* recebido do front-end:

```java
@Component
@Slf4j
public class GoogleTokenVerifier {

    private final GoogleIdTokenVerifier verifier;

    // O Client ID é lido da propriedade google.client-id do application.yml
    public GoogleTokenVerifier(@Value("${google.client-id}") String clientId) {
        // O verificador é criado uma única vez, pois ele mantém em cache as chaves públicas do Google
        this.verifier = new GoogleIdTokenVerifier
                .Builder(new NetHttpTransport(), GsonFactory.getDefaultInstance())
                // o token deve ter sido emitido pelo Google
                .setIssuers(List.of("https://accounts.google.com", "accounts.google.com"))
                // o token deve ter sido emitido para a nossa aplicação
                .setAudience(Collections.singletonList(clientId))
                .build();
    }

    public GoogleIdToken.Payload verify(String idTokenString) {
        GoogleIdToken idToken = null;
        try {
            idToken = verifier.verify(idTokenString);
        } catch (Exception e) {
            log.error("Erro ao validar o ID Token do Google: {}", e.getMessage());
        }
        if (idToken == null) {
            throw new InvalidGoogleTokenException();
        }
        return idToken.getPayload();
    }

    public static class InvalidGoogleTokenException extends RuntimeException {
        public InvalidGoogleTokenException() {
            super("Google ID Token inválido.");
        }
    }
}
```

O método `verifier.verify(...)` realiza as seguintes verificações:

- **Assinatura**: o *token* foi assinado com uma das chaves públicas do Google;
- **Emissor (`iss`)**: o *token* foi emitido por `accounts.google.com` (valores definidos em `setIssuers`);
- **Audiência (`aud`)**: o *token* foi emitido para a **nossa** aplicação, ou seja, o `aud` do *token* é igual ao Client ID informado em `setAudience`. Sem essa verificação, um *token* gerado para qualquer outro site que usa "Login com Google" seria aceito pela nossa API;
- **Expiração (`exp`)**: o *token* ainda está dentro do prazo de validade.

Se alguma verificação falhar (ou o *token* estiver malformado), é lançada a exceção `InvalidGoogleTokenException`. Caso contrário, é retornado o **Payload** do *token*, de onde são extraídas as informações do usuário (`getEmail()`, `getEmailVerified()`, `get("name")`, ...).

> ⚠️ O ID Token nunca deve ser escrito nos *logs* da aplicação: enquanto não expirar, ele pode ser utilizado por qualquer pessoa para se autenticar na API.

## 4. 🚪 Criando o endpoint de autenticação social

A classe **SocialAuthController**, criada em **`security/social/SocialAuthController.java`**, expõe o *endpoint* `POST /auth-social`. O ID Token é recebido no *header* **`Auth-Id-Token`** (no formato `Bearer <idToken>`).

> O nome da classe não pode ser `AuthController`, pois já existe uma classe com esse nome no pacote `controller` (*endpoint* `/auth/user-info`). O Spring registra os *beans* pelo nome simples da classe (`authController`) e a aplicação não iniciaria por conflito de nomes.

```java
@Tag(name = "Authentication")
@RestController
@RequestMapping("auth-social")
@Slf4j
public class SocialAuthController {

    private final GoogleTokenVerifier googleTokenVerifier;
    private final UserService userService;
    private final UserRepository userRepository;

    // construtor com a injeção das dependências...

    @PostMapping
    public ResponseEntity<AuthenticationResponse> auth(
            @RequestHeader(value = "Auth-Id-Token", required = false) String idToken) {
        if (idToken == null || idToken.isBlank()) {
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
        }
        try {
            // 1. Valida o ID Token recebido do Google
            GoogleIdToken.Payload payload = googleTokenVerifier.verify(
                    idToken.replace(SecurityConstants.TOKEN_PREFIX, ""));

            // 2. Só aceita contas com o e-mail verificado pelo Google
            if (!Boolean.TRUE.equals(payload.getEmailVerified())) {
                return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
            }

            // 3. O e-mail da conta Google é utilizado como username
            String username = payload.getEmail();
            User user = userRepository.findUserByUsername(username);

            // 4. Primeiro acesso: o usuário é cadastrado com a ROLE_USER (definida no UserService)
            if (user == null) {
                user = new User();
                user.setUsername(username);
                user.setDisplayName(getDisplayName((String) payload.get("name"), username));
                // O usuário não conhece essa senha: ele sempre se autenticará pelo Google.
                // Além disso, o JWTAuthenticationFilter bloqueia o login por senha para provider != local.
                user.setPassword(generateRandomPassword());
                user.setProvider(AuthProvider.google);
                userService.save(user);
            }

            // 5. Gera o JWT da API, da mesma forma que o JWTAuthenticationFilter
            String token = JWT.create()
                    .withSubject(username)
                    .withExpiresAt(new Date(System.currentTimeMillis() + SecurityConstants.EXPIRATION_TIME))
                    .sign(Algorithm.HMAC512(SecurityConstants.SECRET));

            return ResponseEntity.ok(new AuthenticationResponse(token, new UserResponseDTO(user)));
        } catch (GoogleTokenVerifier.InvalidGoogleTokenException e) {
            return ResponseEntity.status(HttpStatus.UNAUTHORIZED).build();
        }
    }

    // O displayName deve ter entre 4 e 50 caracteres (validação da entidade User)
    private String getDisplayName(String name, String username) {
        String displayName = (name == null || name.isBlank() || name.length() < 4) ? username : name;
        return displayName.length() > 50 ? displayName.substring(0, 50) : displayName;
    }
}
```

Pontos importantes:

- O **e-mail** da conta Google é utilizado como `username`. Assim, se já existir um usuário cadastrado com o mesmo e-mail, ele será reutilizado (inclusive com as suas *roles*, por exemplo `ROLE_ADMIN`). Por isso só são aceitas contas cujo e-mail foi **verificado** pelo Google (`email_verified`).
- O JWT é gerado com o mesmo `SECRET`, `EXPIRATION_TIME` e algoritmo (`HMAC512`) utilizados no **JWTAuthenticationFilter**. Por isso o **JWTAuthorizationFilter** consegue validá-lo sem nenhuma alteração.
- A resposta utiliza as mesmas classes **AuthenticationResponse** e **UserResponseDTO** do *login* tradicional, portanto o front-end recebe `{ token, user: { displayName, username, authorities } }` em ambos os casos.
- Qualquer falha (*header* ausente, *token* inválido, expirado ou emitido para outro Client ID) resulta em **HTTP 401**.
- As anotações `@Tag` e `@Operation` (no código completo) documentam o *endpoint* no Swagger, disponível em `http://localhost:8080/swagger-ui/index.html`.

## 5. 🔒 Senha aleatória e bloqueio do login por senha para usuários sociais

### 5.1 Gerando uma senha aleatória

O atributo `password` é obrigatório na entidade **User**, então o usuário cadastrado via Google recebe uma **senha aleatória**, que nem ele conhece. A senha é gerada no **SocialAuthController** pelo método `generateRandomPassword()`:

```java
private static final SecureRandom RANDOM = new SecureRandom();
private static final String LOWER = "abcdefghijklmnopqrstuvwxyz";
private static final String UPPER = "ABCDEFGHIJKLMNOPQRSTUVWXYZ";
private static final String DIGITS = "0123456789";
private static final int PASSWORD_LENGTH = 32;

private String generateRandomPassword() {
    List<Character> password = new ArrayList<>();
    // garante ao menos um caractere de cada grupo exigido
    password.add(randomChar(LOWER));
    password.add(randomChar(UPPER));
    password.add(randomChar(DIGITS));
    // completa o restante da senha com caracteres de qualquer grupo
    while (password.size() < PASSWORD_LENGTH) {
        password.add(randomChar(LOWER + UPPER + DIGITS));
    }
    // embaralha para que os caracteres obrigatórios não fiquem sempre no início
    Collections.shuffle(password, RANDOM);

    StringBuilder sb = new StringBuilder();
    password.forEach(sb::append);
    return sb.toString();
}

private char randomChar(String chars) {
    return chars.charAt(RANDOM.nextInt(chars.length()));
}
```

Alguns detalhes da implementação:

- É utilizada a classe **`SecureRandom`**, e não `Random` ou `Math.random()`. A classe `Random` gera uma sequência previsível a partir de uma semente, e por isso não deve ser utilizada para gerar senhas ou *tokens*.
- A senha respeita a mesma regra definida na entidade **User** (`@Pattern`, ao menos uma letra minúscula, uma letra maiúscula e um número), e tem 32 caracteres, muito acima do mínimo de 6.
- Assim como no cadastro tradicional, a senha é criptografada com **BCrypt** pelo `UserService` antes de ser armazenada, e não é devolvida ao usuário.

### 5.2 Bloqueando o login por senha

Como proteção adicional, o **JWTAuthenticationFilter** passou a recusar a autenticação por usuário e senha (`POST /login`) de usuários cujo `provider` não seja `local`:

```java
user = (User) authService.loadUserByUsername(credentials.getUsername());
...
//Usuários cadastrados por meio de uma rede social (ex.: Google) não possuem senha própria
//e só podem se autenticar pelo endpoint /auth-social
if (user.getProvider() != null && user.getProvider() != AuthProvider.local) {
    throw new BadCredentialsException("Usuário deve se autenticar com " + user.getProvider());
}
```

Como `BadCredentialsException` é uma `AuthenticationException`, o Spring Security trata a falha da mesma forma que uma senha incorreta, e o usuário recebe **HTTP 401**.

> ⚠️ Por que isso é importante? Se todos os usuários do Google recebessem uma senha fixa (por exemplo `P4ssword`), qualquer pessoa que conhecesse o e-mail de um usuário conseguiria se autenticar em `/login` com essa senha.

## 6. 🛡️ Ajustando a configuração de segurança

Na classe **WebSecurity**, o *endpoint* `/auth-social` deve ser público, pois é justamente por ele que o usuário obtém o JWT. Também foram mantidas as regras de autorização por *role*:

```java
http.authorizeHttpRequests((authorize) -> authorize
        .requestMatchers(HttpMethod.POST, "/users/**").permitAll()
        .requestMatchers("/error/**").permitAll()
        .requestMatchers("/h2-console/**").permitAll()
        //permite que a rota "/auth-social" (login com o Google) seja acessada sem o usuário estar autenticado
        .requestMatchers("/auth-social/**").permitAll()

        //documentação da API (Swagger)
        .requestMatchers("/v3/**").permitAll()
        .requestMatchers("/api-docs/**").permitAll()
        .requestMatchers("/swagger-ui/**").permitAll()

        // Somente usuários com permissão de admin podem acessar /products (qualquer requisição HTTP)
        .requestMatchers("/products/**").hasAnyRole("ADMIN")
        .requestMatchers(HttpMethod.GET, "/categories/**").hasAnyRole("ADMIN", "USER")
        .requestMatchers("/categories/**").hasAnyRole("USER")
        .requestMatchers("/users/**").hasAnyRole("ADMIN")

        //as demais rotas da aplicação só podem ser acessadas se o usuário estiver autenticado
        .anyRequest().authenticated()
);
```

### 6.1 Header `Auth-Id-Token` no CORS

Como o ID Token é enviado em um *header* personalizado e o front-end executa em outra origem (`http://localhost:5173`), o navegador faz uma requisição *preflight* (`OPTIONS`) perguntando se o *header* é permitido. Por isso o `Auth-Id-Token` precisa estar na lista de `allowedHeaders` do método `corsConfigurationSource()` (a configuração da aula03 já o incluía):

```java
configuration.setAllowedHeaders(List.of("Authorization","x-xsrf-token",
        "Access-Control-Allow-Headers", "Origin",
        "Accept", "X-Requested-With", "Content-Type",
        "Access-Control-Request-Method",
        "Access-Control-Request-Headers", "Auth-Id-Token"));
```

Sem esse ajuste, a requisição para `/auth-social` é bloqueada pelo navegador com um erro de CORS, mesmo com o *endpoint* liberado no Spring Security.

## 7. 🧪 Testando o endpoint

Para testar sem o front-end, é possível obter um ID Token válido copiando o valor de `credential` recebido pelo cliente (por exemplo, com um *breakpoint* na função `onSuccess` da página de *login*) e enviá-lo à API:

```bash
curl -X POST http://localhost:8080/auth-social \
     -H "Auth-Id-Token: Bearer <ID_TOKEN_DO_GOOGLE>"
```

Resposta esperada (HTTP 200):

```json
{
  "token": "eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzUxMiJ9...",
  "user": {
    "displayName": "Nome do Usuário",
    "username": "usuario@gmail.com",
    "authorities": [ { "authority": "ROLE_USER" } ]
  }
}
```

O `token` retornado pode então ser utilizado nas demais requisições, no *header* `Authorization: Bearer <token>`, exatamente como o *token* obtido em `/login`. O novo usuário também pode ser consultado no console do H2 (`http://localhost:8080/h2-console`, JDBC URL `jdbc:h2:mem:pw45s-dev`), na tabela `TB_USER`, com o `PROVIDER` igual a `google`.

Sem o *header* ou com um *token* inválido, a resposta é **HTTP 401**:

```bash
curl -i -X POST http://localhost:8080/auth-social -H "Auth-Id-Token: Bearer token-invalido"
```

> 💡 Lembre-se de que, pelas regras de autorização configuradas na **WebSecurity**, um usuário com apenas a `ROLE_USER` não tem acesso a `/products/**` (restrito a `ROLE_ADMIN`). Para testar com um administrador, atribua a `ROLE_ADMIN` ao usuário na tabela `TB_USER_AUTHORITIES`. Os usuários iniciais (`admin`, `teste`) utilizam a senha `123`.
